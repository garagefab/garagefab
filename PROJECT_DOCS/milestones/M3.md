# M3 — Spec Flow and Evidence

> Status: **Not started**
> Size: L · Depends on: M2
> Covers: `SPC-1..7`, `REV-1..6`, `APR-1..7`, `LOG-3`, `INT-1` (full), review and job-spec validators, clarification handling, evidence builder and `evidence.md`.

## Goal

The `feature` profile works through the API. A `feature` job passes clarification, spec review, review report, and approval gate via the API; Scenarios 2 (without GitHub) and 4 pass.

## Dependency Graph

```text
T1 (Feature profile state machine & INT-1 API)
├── T2 (Spec agent step & draft validation)
│   └── T3 (Clarification flow)
├── T4 (Review agent step & review.json validation)
└── T5 (Evidence builder & evidence.md)
    └── T6 (Approval gates & Reject)
```

## Tasks

> [!NOTE]
> **Medium Detail Level:** This milestone is further out. Tasks should be detailed further when this milestone becomes next.

### T1 — Feature Profile & Job Intake API
**Requirements:** `INT-1`, `PIP-1` (Feature profile)
**What to do:**
- Update the `factory` state machine to implement the `feature` profile (`01` → `02` → `04` → `05` → `06` → `07`).
- Complete the API endpoint for job creation (`INT-1`), accepting `project`, `work_type`, `title`, and `intent text`.
- Write the intent text to `.garagefab/jobs/<id>/intent.md` when the worktree is created.
**Acceptance:**
- A `feature` job can be created via API and reaches stage `02`.
- `INT-1`: Job exists at `01_Intent`/`queued`, intent written to `intent.md`.

### T2 — Spec Agent Step & Draft Validation
**Requirements:** `SPC-1`, `SPC-2`, `SPC-4`, `SPC-5`, `LOG-3`
**What to do:**
- Implement the spec agent runner. Provide prompt instructing to output either `clarification-questions.md` or `spec.md`.
- Implement a validator for `spec.md` enforcing the structure from spec §6.1.
- On valid spec, commit as a checkpoint and move to `02`/`spec_review`.
- On invalid output (neither or both), fail the step as `Flawed` and re-run.
**Acceptance:**
- `SPC-1`: Exactly one file produced, otherwise Flawed.
- `SPC-2`: Agent outputs questions if ambiguous (job goes to `needs_clarification`).
- `SPC-4`: Spec validator enforces structure.
- `SPC-5`: Valid draft committed, job status `spec_review`.
- `LOG-3`: Artifacts stored in job directory.

### T3 — Clarification Flow
**Requirements:** `SPC-3`
**What to do:**
- Implement an API endpoint to post clarification answers for jobs in `needs_clarification`.
- Write answers to `clarification.md` as Q&A blocks (spec §6.4), commit as checkpoint.
- Move job to `02`/`queued`.
**Acceptance:**
- `SPC-3`: Answers accepted via API, file created, job returns to `queued`, next spec run receives them.

### T4 — Review Agent Step
**Requirements:** `REV-1..6`
**What to do:**
- Implement the review agent runner in stage `05`.
- Supply prompt with spec (or intent), diff, and command summary. Do not include coding session context.
- Implement a validator for `review.json` against schema (spec §6.2).
- Enforce that the review step makes no repository changes (revert if any).
- Move to `06`/`awaiting_approval` on success.
**Acceptance:**
- `REV-1`: Fresh session without coding context.
- `REV-2`: `review.json` validated, invalid → Flawed.
- `REV-3`: Warnings don't block.
- `REV-4`: Step reverted and Flawed if agent changes files.
- `REV-5`: Checkpoint commit on success, proceeds to `awaiting_approval`.
- `REV-6`: `request_changes` decision doesn't auto-loop, and it routes `docs` jobs to `06` instead of `07`.

### T5 — Evidence Builder
**Requirements:** `APR-1..4`
**What to do:**
- Create the evidence builder in `factory` that compiles test results, review report, diff stats, and warnings from stored artifacts.
- Implement the API to serve this summary.
- Write the summary to `evidence.md` and commit it.
**Acceptance:**
- `APR-1`, `APR-2`: API returns required data for summary and drill-down links.
- `APR-3`: No new agents/commands run to build evidence.
- `APR-4`: `evidence.md` written and committed.

### T6 — Approval Gates
**Requirements:** `SPC-6`, `SPC-7`, `APR-5..7`
**What to do:**
- Implement Approve/Reject APIs.
- Ensure they only accept dashboard session cookies, refusing bearer tokens (`APR-7`).
- For Spec Review Approve (`SPC-6`): re-read `spec.md`, re-validate, commit, record SHA, advance to `04`.
- For Final Approve (`APR-5`): verify `HEAD` SHA matches the evidence. If stale, return `409`.
- For Reject (`APR-6`): require non-empty note, write `rejections/<n>.md`, advance to `04`/`queued`.
**Acceptance:**
- `SPC-6`, `SPC-7`: Job stuck at `spec_review` until explicit Approve. Spec hash recorded.
- `APR-5`: `409 stale_evidence` if worktree modified after evidence build.
- `APR-6`: Rejection goes to `04`/`queued` with a note.
- `APR-7`: `403` if only bearer token is provided.

## Exit Criteria

- Scenarios 2 (clarification) and 4 (rejection) pass.
- A `feature` job reaches the final gate with complete evidence via the API.

## Risks

- Refer to plan.md §6. None specifically isolated to M3, but general agent output fragility (R2) applies to the spec and review steps. Ensure schemas and validation are strict.
